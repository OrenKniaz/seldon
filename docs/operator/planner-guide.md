# Planning with Seldon

Send the user’s actual words with `harness_chat(text, reply_to?)`. This is the single mutation entry point. Seldon reads the frozen kickoff, calls its configured semantic roles, writes the canonical plan, and continues until a user decision or a held outcome needs attention.

The reply contains the proposal, rationale, current state and next action. Use its opaque `reply_to` token when answering a displayed decision; never construct internal node, finding, request or judgment IDs. Ordinary requests need only text. Read-only status, inspection, schema and cockpit tools remain available.

Provider permission P is separate from Vision Lock A, execution B and acceptance C. Native confirmation preserves its own provenance. A chat-only client can send the exact `/authorize` command with the displayed permission token. The selected kickoff tuples alone never authorize a launch. Chat actors remain unverified.

Use `/confirm` to open a native confirmation for the displayed subject. Use `/pause`, `/resume` or `/stop` for explicit run control. Other directions are interpreted against the current accepted scope and evidence. Changed requirements invalidate the prior displayed consent before another decision is offered.

Malformed semantics receive two exact fixes on the same canonical request, followed by one bounded steering question. Unchanged facts cannot reset that allowance. Unknown launch outcomes are retained for diagnosis; reconnecting does not authorize replay. Verified completed replies can be consumed from their original receipts.

Semantic packets contain the relevant graph, actual dialogue, confirmed memory with provenance and concrete observations. They are fresh for every question. No host-side schema assembly or structured answer submission is needed. Real provider execution and full product acceptance remain separate from fake-provider golden coverage.
